# What is Research Software, and who creates it?

- Code: instructions a computer follows to do "something useful"
- Almost universal: 92% of academics use it; 7/10 say research is impossible without it (UK survey)
- Ranges from a short script to specialised or complex software
- Usually created by researchers themselves, sometimes with RSE help
- Often built informally within a small team

::: notes

- In simple terms: a set of instructions a computer follows to work with data — a bit like a recipe with steps, called "code"
- 92% of academics use research software, and 7 out of 10 UK researchers say it would be impossible to do their research without it (Software Sustainability Institute survey, cited in the Netherlands eScience Center/NWO Practical Guide to SMPs)
- Ranges from a short script that cleans a spreadsheet to specialised interview-coding software or a complex simulation model
- Created by researchers themselves — like Anna and Benji — often with no formal training, sometimes with help from a Research Software Engineer (RSE): a specialist in software, much like you specialise in data
- Often built informally within a small team: postdocs, students, research assistants

:::

# How is Research Software developed and used?

- Grows organically alongside the research, not planned upfront
- Some track changes over time (version control); many just keep files on a laptop
- Used by the creator, colleagues, or others to produce the results behind publications

::: notes

- Grows organically alongside the research, rather than being planned upfront — a rough script slowly becomes a working analysis
- Some teams track changes over time ("version control" — a bit like "track changes" in Word, but for code); many others just keep files on a laptop
- Used by the creator or colleagues, sometimes unrelated people to clean data, run analyses, code interview transcripts, and produce the figures and results behind publications

:::

# Quality, Reproducibility, and Reuse

- Undocumented code can't be checked or reused later — not even by its author
- Well-organised software can save the next person months of work
- High stakes: the black hole image, AlphaFold, and Via Appia reconstructions all relied on reliable software
- Anna: gets a new dataset, wants to rerun the same analysis
- Benji: a bug turns up in his shared coding tool, and every partner site's coded data needs to be checked

::: notes

- If code isn't kept or documented, no one — not even the author — can check how a result was produced, or reuse it later
- Well-organised software often outlives the project/person that made it, and can save the next person months of work
- Concrete stakes: software underlies major discoveries too — the first image of a black hole (Event Horizon Telescope, 2019), AlphaFold's protein structure predictions (2020), 3D reconstructions of the Via Appia (2016). If that software weren't reliable and reproducible, those results couldn't be trusted (Netherlands eScience Center/NWO Practical Guide to SMPs)

- Anna gets a new dataset and wants to rerun same analysis
- Benji: a bug turns up in his shared coding tool, and every partner site's coded data needs to be rechecked — much higher stakes than a bug in a single researcher's own script

"Well organised" here = version-controlled, has a README explaining what it does and how to run it, records its dependencies, and follows a consistent structure — the same basics that later map onto the SMP's core requirements

:::

# Sharing and Citing Software

- Like datasets, software can be stored, shared, and formally cited as a research output
    - Everyday storage: GitHub, GitLab
    - Long-term, citable archiving: Zenodo, institutional repositories (gives a DOI)
- Tools exist, but not widely known/used — seen as extra, a luxury
- Barriers to sharing: "ugly" code, fear of mistakes being found, feels too niche
- Journals exist to publish about research software (JOSS, Software-X,...)

::: notes

- Like datasets, software can be stored, shared, and formally cited as a research output
    - Everyday storage: platforms like GitHub or GitLab; 
    - Long-term, citable archiving: Zenodo or an institutional repository, which gives the software a DOI
- Tools and platforms exist, not everyone knows about them and/or how to use them and integrate them into their workflow; seen as extra and luxury
- Many barriers to sharing code: ugly, not done, what if someone finds a mistake, too niche, ...
- Journals exist to publish about research software (JOSS, Software-X,...)
:::

# What Does an SMP Look Like? (10 min)

::: notes

- Like a Data Management Plan (DMP), but for software: a short, living document on where the code lives, how it's documented, who maintains it, and what happens to it after the project ends
-> Advantage of having SMP separate from DMP: increased understanding of software development as a collaborative project, increased product-intrinsic focus of software development

Core requirements (Netherlands eScience Center / NWO Practical Guide to Software Management Plans, 2022, Section 5.1), grouped by focus (Figure 1):

Engineering focus
- Version control: use a version control system so specific versions of the software can be identified
- Testing: unit, functional, integration, linting, typing, regression tests; document tests and track coverage
- Packaging: use appropriate package managers so users can install/deploy the software with ease
- Software Engineering quality: adhere to code quality standards (styling, modularity) and use tools to measure it

Documentation
- User documentation: explain clearly what the software does and how it should be used
- Deployment documentation: explain system requirements/dependencies and give installation & testing instructions
- Developer documentation: explain how the software can be modified, tested, and contributed to (governance, code of conduct, contributing guidelines)

Project management focus
- Purpose: what problem it solves, intended audience, advantages/limitations
- Repository: deposit releases in a publicly accessible repository with persistent, resolvable identifiers
- Citation: include information on how the software should be cited
- Software licensing and compatibility: assign a licence, and check compatibility with the licences of dependencies
- Maintenance: arrangements for long-term maintenance/reuse; a retirement strategy where relevant
- Support (during the project): plan resources for training, RSE hiring, infrastructure
- Risk analysis: privacy, security, reliability, portability/vendor lock-in

Not every project needs all 14 — see "management levels" (low/medium/high) on the following slides.

:::


![](images/smp_core_requirements.svg)

In plain terms, ask a researcher: where's the code, who else touches it, is it documented, what's the licence?

# When to Advise a Researcher to Look Into an SMP

Ask them: What's it for? What breaks if it fails or isn't maintained? How long does it need upkeep?

Management levels: 

- **Low** → a lightweight checklist is enough (purpose, version control, basic docs, licence)
- **Medium** → suggest the full SMP template (adds repository, testing, citation, maintenance plan)
- **High** → flag for RSE/specialist involvement (adds a support plan and risk analysis)


::: notes

This slide answers: when should you point a researcher toward an SMP, and how far should they take it?

The Netherlands eScience Center / NWO guide (Section 6) proposes scaling SMP requirements to a management level, based on three factors: purpose, reliability (risk to self/others, reputation, research), and maintenance burden.

- Low: e.g. a script that produces one figure for a paper, or a one-off analysis script. Needs only Purpose, Version control, User documentation, Deployment documentation, Licensing. Action: a lightweight checklist is enough — no need to push the full template.
- Medium: e.g. reusable analysis code, a simulation model. Adds Repository, Developer documentation, Citation, Testing, Software Engineering quality, Packaging, Maintenance. Action: worth suggesting the full SMP template.
- High: e.g. production-critical software (a telescope's data pipeline). Adds Support and Risk analysis on top of everything else. Action: bring in an RSE or specialist — this is beyond what a data steward should advise alone.

- Anna's cleaning/analysis scripts → likely low, maybe medium if she plans to share them for reuse by others
- Benji's shared coding tool → medium/high: written together with a couple of fellow PhD students, none of them with special software training, but the whole consortium now depends on it staying correct and consistent — the level comes from impact and scale, not from who wrote it or how complex the code is. This also means version control and shared conventions matter now that multiple people touch the same code.

Organisations define their own management levels, and the level that applies to a project can change as it evolves.

:::

# Why Consider an SMP?

::: {.column}
**For your organization**

- Homogenisation: comparable, reusable software, shared good practice
- Counselling capacity: gives support staff the background to advise well, catches risks early
- Avoids duplicated effort across projects; lets funders verify promised work was done
- Matches what some journals (JOSS, SoftwareX) already expect
- Weighed against: the effort to build/maintain a template, and the need for buy-in

:::

::: {.column}
**For a researcher**

- Traceability and reusability of their own results
- Better documentation, earlier testing, FAIR4RS compliance
- Makes expectations clear early — instead of scrambling once a project is finishing

:::

::: notes

- Homogenisation: When teams follow a common structure for documenting/managing their software (via an SMP), the resulting code looks more similar across projects. That makes it easier to compare different tools, reuse parts of one project's code in another, and spread good habits (consistent style, structure, docs) rather than everyone reinventing their own conventions from scratch.

- Added value for research: An SMP records how the software was built and why certain choices were made. That means someone (including the original author, later) can trace back how a result was produced, and other researchers can pick up the software and reuse it for new work instead of starting over — e.g. Anna rerunning her analysis on a new dataset.

- Quality assurance: Writing an SMP forces documentation to be planned rather than an afterthought, which makes peer review and future use easier. It also encourages testing software early, rather than only at the end. And it naturally pushes projects toward following the FAIR4RS principles.

- Counselling: Having an SMP gives support staff (like RSEs or data stewards) the background they need to advise a project properly. It also surfaces risks early — e.g. if a project plans to rely on proprietary or legally questionable libraries, that's flagged before it becomes a problem — and it helps estimate/control costs (staff time, licenses, infrastructure) up front rather than discovering them late.

- Avoiding duplication: An SMP prompts you to check whether it's more cost-efficient and beneficial for the community to reuse or contribute to existing software, rather than building something new from scratch (Netherlands eScience Center/NWO Practical Guide to SMPs, Section 4)
- Verification of work: For funded projects, an SMP lets funders and the wider community check whether the work promised on software was actually carried out

Several journals (such as SoftwareX and the Journal of Open Source Software (JOSS)) have checklists that are expected to be filled in by the software authors before any submissions, addressing most of the key points of an SMP.

On the organization side, this is weighed against the cost of building and maintaining a template, and needing buy-in from researchers and supervisors — a template no one fills in has no benefit.

:::

# When to Do It?

::: {.column}
**For your organization**

- Cheapest to introduce as policy/template early — e.g. alongside DMP requirements
- Natural moments: funders start asking, support capacity grows, several projects hit the same problems

:::

::: {.column}
**For a researcher**

- Best started at the proposal stage, alongside the DMP
- Revisited at key moments: new team member, funding renewal, project end
- Never too late to start

:::

::: notes

Both perspectives point the same way: earlier and lighter beats later and heavier.

- For a researcher: best started at the proposal stage, alongside the DMP, and revisited at key moments (new team member, funding renewal, project end) — but never too late to start.
- For an organization: introducing a template/policy is cheapest before it needs to be retrofitted onto many existing projects — e.g. tied to DMP requirements, or triggered once a funder starts asking, support capacity grows, or the same gaps keep coming up across projects you support.

:::

# Benefits and Challenges of AI 

::: {.column}
**Benefits for SMPs**

- Can help draft documentation, READMEs, even a first pass at SMP answers
- Lowers the barrier to good practices for less technical researchers
- Can speed up filling in a template by drafting from existing repo content

:::

::: {.column}
**Challenges with writing code**

- Code a researcher didn't fully write is code they may not fully understand — testing and documentation matter more, not less
- Licensing/provenance risk: AI output can reproduce licensed code without attribution
- Reproducibility risk: prompts and models change — what actually produced this result?
- New question for SMPs: should "was AI used, and how" be documented itself?

:::

-> AI doesn't remove the need for an SMP — it raises the stakes on documentation, testing, and provenance

::: notes

This connects back to both decisions: for the org-level question, AI changes the cost side (documentation is cheaper to produce) but adds a new benefit/risk to weigh (provenance, licence compliance). For the researcher-advice question, AI-assisted code is a reason to *raise* the management level, not lower it — the person nominally "writing" the code may understand it less than someone who wrote it by hand, and AI models change over time, undermining reproducibility. Some newer SMP/DMP templates are beginning to add an explicit "AI use" disclosure question — worth flagging as an emerging area rather than settled practice.

:::

# Tips and Challenges

- Start small, reuse existing documentation, and make the plan visible to the whole team 
- Common blockers: not knowing where to start (or that scripts even count as "software"), little time, unclear reuse rules, and turnover as students and postdocs leave
- As organization: Provide template and guidance, link to what they already have

# Tools, Templates, and Examples

- Institutional or funder-provided SMP templates, and guidance from organisations such as the Software Sustainability Institute
- GitHub/GitLab for everyday code storage; Zenodo or institutional archives for longer-term, citable archiving
- Examples from other, similarly sized projects to adapt, rather than starting from a blank page

::: notes

- SMP rubric: alongside a template, it helps to produce an assessment rubric — example acceptable/unacceptable answers per question. Useful for guiding researchers and for evaluators, though it takes effort to keep it matched 1:1 to the template (Netherlands eScience Center/NWO Practical Guide to SMPs, Section 5.3)
- The Netherlands eScience Center/NWO guide itself includes ready-made sample SMP templates for low/medium/high management levels (Section 6.3) — a good starting point to adapt rather than building templates from scratch

:::

# Current Practices, Policy, and Trends

- Still emerging and less standardised than DMPs so far — practice varies a lot by field and institution
- National funders and open science policy (the FAIR principles) are increasingly extending from data to software
- Growing recognition of software as a citable research output, and a growing number of specialist roles (like RSEs) supporting it
